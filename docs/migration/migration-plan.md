## 1. How to read this plan

### 1.1 The three hard requirements

Every step in this plan satisfies all three:

| Requirement | How it is guaranteed |
|---|---|
| **Reversible** | One step = one PR = one squashed commit = one `git revert`. Every step declares a reversibility class (§1.3) and an explicit rollback procedure. No step depends on a later step to be correct |
| **Independently testable** | Every step declares validation commands that pass **on that step alone**, without any later step being applied. `main` is releasable after every step |
| **Low risk** | Blast radius limited to one package wherever possible; the destructive half of any change is always a separate later step (§2.1); every step is gated by an automated check that existed **before** the step began |

### 1.2 Field definitions

| Field | Meaning |
|---|---|
| **Purpose** | The single outcome. If a step needs the word "and" twice, it should be split |
| **Files affected** | Concrete paths, verified against commit `01c532e`. `(new)` marks a file that does not exist yet |
| **Risk** | Low / Medium, with the specific failure mode named. See §1.4 |
| **Rollback** | Exact procedure, including any external state (config files, databases) that must also be restored |
| **Validation** | Commands that must pass. Every step also inherits the global gate (§1.5) |
| **Complexity** | T-shirt size with an indicative engineer-day range. XL is prohibited — split it |

### 1.3 Reversibility classes

| Class | Meaning | Recovery time |
|---|---|---|
| **R1** | Pure `git revert`. No build artifacts, no external state | < 1 min |
| **R2** | `git revert` + `npm run build` | < 5 min |
| **R3** | `git revert` + rebuild + restore `~/.claude.json` from the installer's automatic backup | < 10 min |
| **R4** | `git revert` + rebuild + re-index the code graph | < 15 min |

Every step in this plan is R1–R4. **No step is irreversible.**

### 1.4 Risk definitions

| Level | Definition |
|---|---|
| **Low** | Blast radius is one package. Revert restores the prior state with no external side effects. A pre-existing automated gate detects the failure |
| **Medium** | Touches shared build substrate, external config (`~/.claude.json`), or a security-relevant code path. Requires manual verification in addition to automated gates |

**There are no High-risk steps in this plan.** The two items that would be High have been neutralized:

- **Workspace hoisting vs. native dependencies** — decomposed into a throwaway spike (S-07) that produces a decision record and is never merged. S-09 only proceeds if the spike passes.
- **Migrating a 2,051-LOC `index.ts` with a 43-branch dispatch switch** — decomposed into eleven steps across Phases G and H, each moving one concern, behind a coexistence adapter that lets old and new dispatch run side by side.

### 1.5 The global gate

Every PR, at every step, must pass:

```bash
npm run typecheck          # all packages
npm run build              # all packages
npm run test               # unit + guards
npm run smoke              # all servers start over stdio and answer health_check
npm run contract:verify    # tool surface unchanged vs. golden snapshot  (from S-06)
```

Before S-04 these run per-package; from S-04 they are root aggregates.

### 1.6 Non-negotiable sequencing rules

1. **Never combine an extraction with a behavior change.** Extract first, change second, in separate PRs.
2. **Never delete a duplicate in the same PR that introduces its replacement.** See §2.1.
3. **Never run two phases concurrently.** Each changes the substrate the next one assumes.
4. **Never change the tool surface and the implementation in the same PR.** `contract:verify` must be able to distinguish "refactor" from "API change".
5. **Never skip Phase A.** Everything downstream depends on the safety net existing first.

## 2. Risk control mechanisms

### 2.1 The Strangler Triplet

Every shared-code extraction is three separate, independently revertible PRs:

| Sub-step | Action | Risk | Why it is safe |
|---|---|---|---|
| **A — Add** | Create the new shared package. **Zero consumers.** Full unit tests | Low | Nothing imports it. Reverting deletes a leaf |
| **B — Migrate** | Point consumers at the shared package. Old copies remain on disk, now unused | Low | Behavior verified by `contract:verify` + smoke. Reverting restores the old import line |
| **C — Delete** | Remove the now-unreferenced copies | Low | `guard:deps` has already proven they have zero importers. Pure deletion |

This is why no extraction step is Medium risk. **Sub-step B is the only one that can change behavior, and it changes exactly one import path per file.**

### 2.2 The golden contract snapshot

S-06 captures the complete `tools/list` response of all four servers — 76 tools, their schemas, descriptions, and annotations — as committed JSON. `npm run contract:verify` diffs live output against it.

This is the single most important net in the plan. It converts "did we accidentally change the public API?" from a review question into a build failure. **Every subsequent step's validation references it.**

### 2.3 Coexistence adapters

Phase H migrates 43 tools. Rather than one large change, an adapter lets the new registry and the legacy `switch` serve tools simultaneously: the registry is consulted first, the `switch` handles the remainder. Tools migrate in batches of five to ten. At every point the server is fully functional, and reverting one batch reverts ten tools, not forty-three.

### 2.4 Phase tags and config backups

- Tag `migration/phase-<X>-complete` at each phase boundary. Rolling back a whole phase is `git revert` of a known range.
- The installer already backs up `~/.claude.json` before writing. Any step touching registration is R3 and cites that backup.
- Before Phase C: copy `mcp-local-index-central.db` to `mcp-local-index-central.db.pre-migration`. It is gitignored, ~334 MB, and cheap insurance for R4 steps.

### 2.5 What is explicitly out of scope

Deliberately excluded so no step's blast radius silently widens:

- Any change to tool names, input schemas, or response shapes. This is a **structural** migration.
- Any new feature or new tool.
- Any dependency version bump (except adding the workspace protocol).
- The `servers/` directory move, the server-key rename, and env-prefix unification — all deferred to Phase K behind an explicit go/no-go.

## Phase B — Native Dependency Spike

---

### S-07 · Workspace hoisting spike for native modules (throwaway)

**Purpose**
Determine — before committing to npm workspaces — whether `better-sqlite3`, `tree-sitter` plus its four grammars, `sqlite-vec`, and the platform-pinned `sqlite-vec-windows-x64@0.1.9` survive workspace hoisting on Windows. Phase 0 identified this as the single most likely cause of migration failure.

**Files affected**
- **None on `main`.** All work occurs on a throwaway branch `spike/workspaces-native`, which is **deleted, not merged**.
- Merged to `main`: `docs/adr/0001-workspace-native-deps.md` *(new)* — the decision record only

**Method**
1. Branch from `main`; add a root `workspaces` array; delete the four package-locks; `npm install`.
2. Verify `better-sqlite3` loads and `codebase-index-mcp` completes a full index run.
3. Verify all four tree-sitter grammars parse (`npm run test:extractor`, `test:csharp-parser`).
4. Verify `sqlite-vec` loads and vector indexing populates (baseline: 990 symbols).
5. Verify `npm run smoke` for all four servers.
6. Record: what worked, what needed `.npmrc` settings (`install-strategy=nested`, `legacy-peer-deps`, per-package `node_modules`), and residual concerns.

**Risk** — **Low**, by construction. The branch is never merged. The only `main` artifact is a markdown ADR.

**Rollback** — R1. Delete the branch; revert the ADR.

**Validation**
- ADR states a clear **GO** or **NO-GO** for S-09, with reproduction steps
- If GO: the exact `.npmrc` contents required are recorded verbatim
- If NO-GO: the ADR proposes the fallback (keep four `node_modules` via `install-strategy=nested`, or exclude `codebase-index-mcp` from the workspace and depend on shared packages by relative `file:` reference)

**Complexity** — **M** (1–2 d)

> **This step is a prerequisite for S-09 and must not be skipped.** A NO-GO does not stop the migration — it changes S-09's implementation only.
