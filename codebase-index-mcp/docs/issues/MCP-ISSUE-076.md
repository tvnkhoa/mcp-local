## MCP-ISSUE-076 — Text and JSON lanes: configs, data files and package manifests were invisible

- **Status:** ✅ FIXED 2026-10-20 (release F item 10 of the wec.aria adoption plan).
- **Scenario:** wec.aria's health skip report listed 612 `.json`, 13 `.jsonl` (5 `unknown_extension`, 8 `likely_minified` — one-line JSON is normal), 5 Dockerfiles, YAML, shell, nginx `.conf` / `.template`, `.envsh`, `.example`, `.code-workspace` and the dotfile configs as `unknown_extension` or `excluded_extension`. `search_regex` reached them only with `scanAll`, `search_literals("gd-020")` could not find the eval case that names it, and no tool could say which workspace package depends on which.
- **Fix:**
  - **Text lane** (`extractors/plainTextExtractor.ts`, language `text`): YAML, Dockerfile (`Dockerfile`, `Dockerfile.*`, `*.dockerfile`), Makefile, `.sh`, `.envsh`, `.conf`, `.template`, `.txt`, `.example` / `.sample`, `.code-workspace`, `.toml`, JSONL / NDJSON and the dotfile configs (`.editorconfig`, `.gitattributes`, `.gitignore`, `.dockerignore`, `.nvmrc`, …; `TEXT_FILENAMES` in `fileFilter.ts`, matched on the whole name since `extname(".gitignore")` is `""`). A `module` symbol and no other symbol. Literals: JSONL string values per line, single-line quoted strings outside `#` comments, YAML plain scalars.
  - **JSON lane** (`extractors/jsonExtractor.ts`, language `json`): every `.json` is a module whose string values are literals (on the line their quoted form first appears). `package.json`: the module's `signature` is `npm:<name>`; `DEPENDS_ON npm:<pkg>` per entry of `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies`, reason `npm <section> (<range>)`, kept as labelled tokens like `nuget:` (kept out of the cross-repo window in `resolveUnlinkedEdges`, never counted as unresolved). Workspace edges: post-phase `graph/edgeResolverPackages.ts` adds `DEPENDS_ON` to the `package.json` module of a same-repo package a dependency names (`workspace package <name> (<range>)`; 1.0 for `workspace:`, 0.95 for a plain range), recomputed whole every run so incremental equals full. `tsconfig*.json` / `jsconfig*.json`: `IMPORTS` for `extends` (a relative spec gets `.json`; a package spec is labelled `npm_package`), `references[].path` (a directory means its `tsconfig.json`) and `compilerOptions.paths` targets joined to `baseUrl` (a `*` target is a labelled token `tsconfig paths glob (…)`). JSONC through the existing `stripJsonComments` (now exported from `moduleResolution.ts`); an unparseable file keeps its module and quoted strings and is not a parse failure.
  - **Literal cap order**: the per-file literal cap (100 under the `large` profile a cold-start full run picks, 200 otherwise) is applied after ranking identifier-shaped values (one token, ≤ 80 chars) ahead of prose. In reading order it ran out at line 9 of `evals/cases/guardrails.jsonl` and `gd-020` (line 20) never reached the lane — found by the live check, not by the fixture.
  - `likely_minified` no longer applies to `.json` / `.jsonl` / `.ndjson` / `.svg` (`isMinifiedCheckExempt`, shared with `search_regex`, which applied the same heuristic to indexed files).
  - **Secrets**: `.env`, `.env.*` (not `.example` / `.sample` / `.template`), `.npmrc`, `*.session`, `*.key`, `*.p8` and the existing key / credential names are never read; the skip reason is now `secret_file` (was `excluded_filename`). `redactSensitive` still runs on every file before any lane sees it. Dead `EXCLUDED_EXTENSIONS` entries (`.env`, `.gitignore`, … — `extname` never returns those) were removed.
  - `INDEX_VERSION` → `v7-text-json-html-svg` (with 077–079).
- **Live** (wec.aria @ `1445bdf`, full run of the built lane into a temp DB, 0 parse failures, 32.4 s; pre-change build 19.9 s): files indexed 2048 → 2767 — `json` 612, `text` 37 (5 Dockerfiles, 13 `.jsonl`, 4 `.txt`, YAML, nginx, `.envsh`, dotfiles, `.code-workspace`, 2 `.env.example`). `search_literals("gd-020")` → `evals/cases/guardrails.jsonl:20`, coverage high. 98 `npm:` edges from 16 `package.json` files (e.g. `checks/data-access/violations/crm-sql-driver-declared/package.json → npm:tedious`, "npm devDependency (^18.6.1)"); 18 workspace edges (e.g. `packages/api/package.json → packages/core/package.json`, "workspace package @aria/core (workspace:*)"). tsconfig: every package `extends` resolves to `tsconfig.base.json`, test configs to their package's `tsconfig.json`; `tsconfig.paths-bypass.json`'s `@aria/*` glob is a labelled token. `search_regex("FROM node")` without `scanAll` → the 5 Dockerfiles. Skip report after: `unknown_extension` only `.sql` (117 — the SQL lane, item 13); `excluded_filename .txt` 1 (`packages/dep-lint/samples/README.txt`, the README rule); `.env` / `.session` gitignored.
- **Guarded:** `fileFilterReleaseF.test.ts` (8 tests), `textLanes.test.ts` (12 tests: quoted / YAML / JSONL literals, the cap, module-only files, package.json tokens and signature, tsconfig JSONC edges, text-level JSON, unparseable JSON, HTML, Vue asset imports); `test:text-json-lane` (75 checks, real MCP stdio on a git fixture): languages, module-only, skip reasons, `search_literals` / `search_regex`, npm tokens and the workspace edge (incl. a plain range after an edit), tsconfig resolution, the separator invariant, I1 = I2 = 0 after every run, the no-op incremental fast-skip, incremental B = dirty B′ = full C on S1–S3, every edge and every literal.
- **Not done here:** `.sql` (item 13); `.xml` / `.props` / `.targets` / `.http` / `.ps1` stay `unknown_extension`. YAML keys, multi-line strings and block scalars are not literals. Package-name links across repos (`npm:` → another repo's `package.json` signature) are possible from the stored signature but not wired into the cross-repo pass.
- **Found on the way (not fixed):** the `auto` performance profile picks `large` for a cold-start full run with `maxFiles ≥ 8000` and `standard` once the repo has rows. The two have different literal caps (100 / 200), so a file unchanged since a cold-start run and the same file after a later full run differ in literal rows — an incremental-vs-full mismatch with no incremental cause. The harnesses pin `CODEBASE_INDEX_LARGE_REPO_PROFILE=standard`. **Fixed in the follow-up below.**
- **Follow-up — one literal cap for every profile (release I6b, ✅ FIXED 2026-10-21):**
  - **Fix:** `resolveLiteralPolicy(profile)` in `extractors/treeSitterExtractor.ts` is gone; every lane (code, Vue script, text, JSON) reads one `LITERAL_POLICY` — `minLength` 6, `maxPerFile` `DEFAULT_MAX_STRING_LITERALS_PER_FILE` = **200** (the old `standard` value, which every repo with rows already ran under; `very-large` was 50, `large` 100). The env overrides `CODEBASE_INDEX_MIN_STRING_LITERAL_LENGTH` / `CODEBASE_INDEX_MAX_STRING_LITERALS_PER_FILE` still apply, to every profile alike. Nothing else that varies by profile reaches literal rows: the edge policy and the post-phase policy change edges only, and a literal's `enclosingSymbolId` comes from the symbols, which no profile changes. The keep order was already deterministic — reading order for code (`literalExtractor`), identifier-shaped values first then prose, each in reading order (a stable partition) for text / JSON (`LiteralCollector`).
  - **Payload:** at most 200 rows per file, one per distinct value. On wec.aria 65 of 1968 files with literals exceed 100 rows; the cold-start full run stores 47 196 rows (was 44 339 under `large`).
  - `INDEX_VERSION` → **`v10-literal-cap`** (generation 10 — other lanes bump it too; reconcile at merge). The bump lifts the fast skip only: an unchanged file keeps its content hash, so an index last built under `large` / `very-large` needs one `mode:"full"` run to store the 200-cap rows.
