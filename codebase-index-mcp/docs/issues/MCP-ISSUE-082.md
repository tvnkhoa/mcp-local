## MCP-ISSUE-082 — SQL lane: migrations were skipped, so "who touches table X" had no answer

- **Status:** ✅ FIXED 2026-10-21 (release H, item 13 of the wec.aria adoption plan).
- **Scenario:** wec.aria keeps its schema in 117 PostgreSQL `.sql` files (`db/migrations/`, `archive/`, seeds, check fixtures) and queries it from TypeScript through raw `pg` (`client.query(…)`, statements kept as `const X = \`insert into …\`` in `*-sql.ts` files). `.sql` had no `LANGUAGE_BY_EXTENSION` entry, so every file was skipped as `unknown_extension`; no tool could list the migrations, grants, policies, functions or TS sites that touch `audit_events`, and the adoption replay counted 2 `.sql` misses as `not_indexed`.
- **Tool/query attempted:** `search_symbols("audit_events")`, `get_call_chain(direction:"callers")`, `health_check` skip report.
- **Expected vs actual:** expected the table, its ALTERs/GRANTs/policies and the TS query sites; got nothing (no symbol), `.sql` listed under `unknown_extension`.
- **Fix:**
  - `services/extractors/sqlLexer.ts` — lexer + statement splitter: `--` / nested `/* */` comments, `'…'` / `E'…'` / `"…"`, `$$` / `$tag$` bodies, psql meta-commands (own statement kind), `COPY … FROM stdin` data, `BEGIN ATOMIC … END` (CASE-aware). Never throws.
  - `services/extractors/sqlExtractor.ts` — per statement: `pgsql-ast-parser` **12.0.2** (exact pin, MIT, pure JS, deps `moo` + `nearley`, no install script), then a token reader per statement head for what it rejects (on wec.aria 622 of 1495 statements: GRANT 144, CREATE POLICY 85, REVOKE 85, DROP POLICY 73, COMMENT ON 61, ALTER TABLE … ENABLE RLS / ONLY 41, ALTER TYPE 35, CREATE OR REPLACE FUNCTION with options 18, DROP TRIGGER 17, ALTER DEFAULT PRIVILEGES 16, CREATE [CONSTRAINT] TRIGGER 13, ALTER FUNCTION 9, …), then a **named gap** (`sql_gap`, `gap: <first words>`, parser message in the signature). DDL inside `DO` bodies (`if not exists … then create role x; end if;`, guarded `create policy`) goes through the same readers, marked `[do block]`; the rest of a DO body is token-scanned.
  - Symbols, **one per definition site** (signature = `<qualified name> — <detail>`, the resolver keys on the qualified part, `name` stays bare for search): `sql_table`, `sql_column` (child of its table; also at `ALTER TABLE … ADD COLUMN` — "where is column Y defined" lists every site), `sql_view`, `sql_index`, `sql_function`, `sql_type`, `sql_role`, `sql_schema`, `sql_sequence`, `sql_policy`, `sql_trigger`; `sql_statement` for a touch without a definition (ALTER, GRANT/REVOKE named like `grant select, insert on table public.audit_events to aria_ingest`, DROP, top-level DML). `COMMENT ON` is documentation: a module → object edge with the line in the reason. `SET search_path` qualifies later unqualified definitions in the file.
  - Edge types (new; not `IMPORTS`/`PROPERTY_REF`, whose meaning other tools read): `SQL_USES`, `SQL_REFERENCES` (FK, from the column), `SQL_GRANT` (object + grantee; owner), `SQL_QUERY` (TS → SQL), `SQL_MIGRATION_ORDER` (numbered file → predecessor in its directory, `NNNN-x.down.sql` → `NNNN-x.sql`; not `IMPORTS`, which would put every migration in every earlier one's import closure). The first four are in `CALL_TRAVERSAL_EDGE_TYPES`. A `LANGUAGE sql` function body is parsed; PL/pgSQL is token-scanned and the reason says `tokenized`.
  - `services/extractors/sqlQueryScan.ts` — token scanner shared by TS literals, PL/pgSQL bodies, DO blocks and policy expressions: tables after FROM (whole list)/JOIN/INSERT INTO/UPDATE/DELETE FROM/TRUNCATE/TABLE, CTE names and aliases excluded; migration-made function calls (`from usage_in_period($1)`; built-ins, casts and aliases excluded); columns **only when unambiguous** (insert list, update set, single-table select list with no subquery) — a multi-table statement makes no column claim.
  - `services/extractors/jsSqlQueries.ts` (TS/JS) — (1) the first argument of `<x>.query(…)` / `.query<T>(…)` (tree-sitter reads `await c.query<T>(…)` as a call on the await expression; unwrapped); (2) every SQL-shaped const; (3) a function naming a SQL-shaped const of its own file (`one(SELECT_USAGE_IN_PERIOD, …)`). `${CONST}` of a same-file string const is inlined (ConversationStore's `${MESSAGE}`); any other `${…}` is a placeholder, and one in a table position is a `sql_gap`. **Not followed:** imported consts at their use site (the const's declaration carries the edge), `read.statement`-style member arguments.
  - `services/graph/edgeResolverSql.ts` — post-phase, by name: `public.x` ≡ `x`; `schema.x` binds only inside `schema` (never another schema's `x`); an unqualified `x` with no default-schema definition binds to the ONE other schema that defines it (`search_path`, 0.5); two or more → kept as `unresolved sql token (ambiguous: …)`. Reason `name_resolved[ (N definitions | search_path | schema-wide, N objects)]: <clause> | <token>`, confidence **0.6** — never exact/high; `isNameOnlyEdgeReason` makes coverage refuse `high`. `ON ALL TABLES IN SCHEMA s` / default privileges fan out to the schema's tables, labelled `schema-wide`. The bound set is rebuilt from tokens + earlier bindings every run (full = incremental); a token that stops binding is restored, never dropped. Unbound tokens are in `UNRESOLVED_SYMBOL_TOKEN_PREFIXES` and excluded from the cross-repo bridge.
  - Tools: `get_call_chain` rows for a SQL hop carry `fromKind`/`fromLine` (callers) or `toKind`/`toLine`, `provenance: "name_resolved"` and `reason`, at nano and compact; `health_check.sqlLane` = `{sqlFiles, gaps, gapSamples[file, line, name]}`; `dead_code_scan` excludes `sql_*`; the `query_graph` description lists the edge types (contract snapshot updated). `query_docs mode:"term"` unchanged.
  - `INDEX_VERSION` → `v9-sql-lane`.

### Follow-up — release I3 (one current definition) and I4 (imported query consts followed), 2026-10-21

- **Scenario (wec.aria reviewer, H note):** the resolver wrote one edge per DEFINITION SITE. Every table declared in an `archive/` migration and again in `0001-baseline` had 2 copies of every caller; `usage_in_period` (4 sites) gave each grant and the TS caller 4 identical rows; `audit_events` showed 142 `SQL_USES` edges for 71 statements. And a TS query const imported into a store file carried its edge only at the const's declaration — "who runs this insert" did not reach the calling function.
- **I3 — fix (`services/graph/sqlDefinitions.ts`, `edgeResolverSql.ts`):**
  - **One current definition per (kind, schema, name).** Rank `(tier, number, file name, path, line)`, highest wins: tier 0 `*.down.sql` (a rollback restores an older shape — never current while an up file defines the name), tier 1 unnumbered files (seeds, check fixtures), tier 2 numbered files under an `archive/` path segment, tier 3 every other numbered migration. So a baseline beats any archive file regardless of number, `0043` beats `0001`, and a later `CREATE OR REPLACE` in one file beats an earlier one. `.down.sql` files are kept as definition SITES (they appear in `alsoDefinedAt`, and their bodies keep their reads) but are never chosen.
  - **Inbound binds to the current definition only; outbound stays per version.** A grant, ALTER, policy, comment, FK or TS query naming `x` gets one edge, reason `name_resolved (current of N definitions): …`. Each definition symbol keeps the edges its OWN body emits, so `usage_in_period` in `0043` reads `turn_quality` and the baseline version does not — and those reads bind, in turn, to the current definition of what they read. Schema-wide grants fan out to current definitions only. A definition naming itself (recursion) is not bound.
  - **`alsoDefinedAt` is derived, not stored.** `getSqlDefinitionInfo` applies the same rank to the `symbols` table at read time; `search_symbols` (every profile), `get_symbol_detail` and `get_call_chain` return `sqlDefinition: {current, definitions, currentDefinition, currentSymbolId, alsoDefinedAt[file:line], note}` for a SQL definition whose name has ≥ 2 sites. Nothing to migrate, nothing that can disagree with the bound edges (the resolver runs at the end of every run on the same table). A superseded site's `get_call_chain` is empty and says which site is current.
- **I4 — fix (`jsSqlQueries.ts`, `edgeResolverSql.ts`):**
  - `.query(B)` / `.query<T>(B, …)` with `B` imported (`import { A as B } from './x.js'`; `ns.A` via `import * as ns`; type-only imports ignored) emits an anchor `sqlconst:./x.js#A` from the calling symbol, clause `ts query imported const B (line N)`. The resolver resolves the specifier from the caller's file (`resolveModuleSpecifier`, tsconfig aliases), finds the exported `variable` `A` there or one import hop on (barrel `export { A } from` / import-then-export, unambiguous only), and if that const carries its own SQL scan (`ts sql const A …`) writes caller → const (`name_resolved … | sqlconst:…`) plus the const's targets as the caller's own tokens, clause `ts query imported const B via A (file:line) <clause> (line N)`, bound like any token (name_resolved, 0.6). A const that is not SQL-shaped, not found, or outside the repo leaves the anchor as `unresolved sql token (not a sql const | no exported const | module not in the repo): …` — no SQL target. `sqlconst:` is in `UNRESOLVED_SYMBOL_TOKEN_PREFIXES`.
  - Full = incremental: the anchor persists with the caller's file (a token, or bound with the token in its reason); every DERIVED edge is deleted and rebuilt from the anchors each run, so a changed or row-shifted const reaches an unchanged caller.
  - Same-file: `.query(read.statement)` (member of a same-file const object literal) is read; a same-file const at `.query(` now says `ts query const X via X (file:line)` too.
  - **Found on the live run:** the extractor's cheap gate `\.query\s*(?:<[^>]*>)?\s*\(` failed on nested type arguments (`.query<Record<string, unknown>>(`), so a file whose only SQL was imported (`packages/ingest/src/store-notifications.ts`) was skipped whole. Now `<[^()]{0,300}?>`.
