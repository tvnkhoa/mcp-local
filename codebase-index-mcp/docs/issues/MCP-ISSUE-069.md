## MCP-ISSUE-069 — a deleted or reverted dirty file survived as a phantom, reported as current

- **Status:** ✅ FIXED 2026-10-20 (P1; found by wec.aria's acceptance of release B, which rejected R1). The gate's refresh moved to a worker thread (release I1b): follow-up below, 2026-10-21.
- **Scenario:** on wec.aria, with a clean tree at HEAD:
  - Create an untracked `zz-r1-probe.mjs` with `export function r1_probe_acceptance_zq7()`. `search_symbols` finds it, via the R1 gate's dirty-mode refresh.
  - Delete the file.
  - `search_symbols` still finds it, with no freshness block and later `coverage: "high"`. `health_check` says "index is up-to-date".
- **Causes (three):**
  - Dirty mode re-reads only what is dirty NOW. A file that stopped being dirty — deleted, or reverted — is never looked at again.
  - `evaluateIncrementalSkip` trusted a clean tree at the indexed commit. After a dirty run the index holds working-tree content, so that proves nothing. An explicit `index_repository(mode:"incremental")` skipped too.
  - The gate cached a "fresh" verdict for 3 s, serving the phantom silently inside that window.
- **Fix:**
  - A dirty-run ledger beside the index DB (shared by every server process) records the paths the index holds from the working tree. When one is no longer dirty, the gate runs `incremental`, which re-hashes every file and prunes the gone. `index_repository` and the watcher keep the ledger current.
  - The skip gate never skips when the last run that did work was `dirty`.
  - No reused "fresh" verdict. The tree is read with one `git status --porcelain=v2 --branch -z`: about 110 ms on wec.aria, against about 330 ms for the previous four spawns.
  - `health_check` names files indexed from a working tree that has since changed, and does not report `ready`.
- **Guarded:**
  - `test:query-refresh` (19 checks): untracked create → found → delete → gone; tracked edit → found → revert → gone, with committed symbols intact; `health_check` names the pending file; an over-budget cleanup is not "high".
  - `runPolicy.test.ts` (the skip rule) and `statusPorcelain.test.ts` (the parser).
- **Follow-up 2026-10-21 (release I1b) — the gate's refresh runs in a worker thread.** wec.aria's reviewer set the acceptance: every read tool answers within the budget + 1 s (first call included), a landed dirty run answers `search_symbols` < 1 s and a warm `find_field_accesses` < 0.5 s, a concurrent call on another repo < 1 s, B.1 unchanged — and no server-thread block > 250 ms during a refresh.
  - **Before** (profile of the built runner on a temp copy of the central DB, wec.aria with 4 dirty files): the dirty run took 27.7 s (resolve 23.3 s of it: calls 11.8, types 4.1; FTS rebuild 4.9) and blocked the event loop up to **8 032 ms, 13 blocks > 250 ms**. Through a fresh server over stdio (the live check below, the release-I build): max block **7 756 ms, 18 blocks > 250 ms** in a 37.6 s refresh window; `search_symbols` on wec.be during it 525-6 960 ms; a trivial `list_repositories` up to 7 564 ms (p50 1 876 ms).
  - **Design.** `services/indexing/refreshWorker.ts` + `refreshWorkerClient.ts` (same folder: `new URL("./refreshWorker.js", import.meta.url)`). One worker per process, spawned and warmed at server start when R1 is on (a cold worker spent seconds loading the indexer and opening its connection inside the first query's budget — `test:field-access-vue` then left the field worker 0.6 s and answered `gap`) and kept; it opens its own `GraphStore` on the same DB file (WAL; the existing 30 s `busy_timeout` covers checkpoints) and runs the unchanged `createIndexRunner` — so the release F guard (`newerBuildRefusal` against the worker connection's latest run, at run start, before any write) applies inside the worker. The gate is handed `refreshWorker.run` in place of the in-process runner; its budget, `serialize`, lock files, dirty-run ledger, `markTriggered` and the `refreshing` / `stale` notes are untouched. A worker `error`/`exit` rejects every outstanding run → the gate answers "the refresh run failed" (stale) and releases the lock; the next query respawns the worker and retries. After a run lands the server thread clears its vector-search memo (`GraphStore.invalidateProcessCaches`); every other read (latest run, the field worker's run key, FTS) is SQL on the server's own connection and sees the new run directly. **`index_repository` and the watcher stay on the server thread** (they stream progress through the request; the acceptance is about query-triggered refreshes).
  - **Three more server-thread blocks, found by CPU-profiling the main thread during the refresh** (moving the run alone left blocks of 0.6-1.9 s):
    - `getRepoStaleness` (every read tool) spawned `git rev-parse HEAD` with `execFileSync`; with the refresh's parse workers busy one spawn held the thread up to 1.9 s. `resolveHeadCommitSha` now reads HEAD from the git directory's files first (`readHeadShaFromFiles`: `.git` dir or `gitdir:` file, loose ref in the git dir then `commondir`, `packed-refs`, detached HEAD) and spawns git only when that is not certain (symbolic ref chain, reftable, unborn).
    - The gate's own `git status` (~110 ms on wec.aria, ~300 ms on wec.be, much more under load) was `execFileSync`; it is now `execFile` (`readWorkingTreeStateAsync`). A call that started a run while another was awaiting git joins that run instead of reporting "another server process".
    - A dirty/incremental run dropped the four DB-wide secondary `edges` indexes for its call resolve and rebuilt them after (466 k edges across 11 repos in the central DB). Every concurrent reader in every process full-scanned `edges` meanwhile, and the rebuild cost more than it saved: now only a `full` run, or one resolving ≥ 50 000 unresolved call rows, drops them (`shouldDropEdgeIndexesForResolve`). The wec.aria dirty run fell from 35.7 s to 14.5-16.4 s.
  - **Found beside it:** `get_file_summary(wec.aria, packages/core/adapters/openai/index.ts)` took **86-108 s** with R1 off — no refresh involved. Its `importedBy` query let the planner (no `sqlite_stat1`) put `symbols` outside `edges`: every symbol of the repo × every edge of the repo. `CROSS JOIN` pins `edges` outside: 79 ms.
  - **Live after** (worktree build, fresh server over stdio per phase, `CODEBASE_INDEX_DB_PATH` = a backup-API copy of the central DB, allowed roots wec.aria + wec.be, R1 on with the default 5 s budget; wec.aria @ `c64ed243` dirty from other sessions — 5 files at the final check, 4 earlier; wec.be clean):
    - (1) first `search_symbols` on wec.aria **5 025-5 060 ms**, `freshness: refreshing/dirty`, coverage `medium`. First calls of other read tools during the refresh: `find_impact_files` 490 ms, `get_file_summary` 134 ms, `search_regex` 3 178 ms, `find_field_accesses` 5 020 ms (coverage `gap`: type program still building), `get_symbol_source` 36 ms, `health_check` 541 ms — all < 6 s.
    - (2) after the run landed: `search_symbols` **177-202 ms**; warm `find_field_accesses` (exact, `kb_version_ids` / `audit_event_schema`) **351-459 ms** client-side, worker round trip 166-239 ms.
    - (3) `search_symbols` on wec.be every 0.7 s during the refresh: **229-609 ms**.
    - Lag (the lag-clean phase: only `list_repositories` every 100 ms, `search_symbols` on wec.be and polls on wec.aria during the 17.7 s window): **max 115 ms, 0 blocks > 250 ms** (before: 7 756 ms, 18); `list_repositories` max 120 ms, p50 16 ms.
    - Re-run with the warm-up (the final build; this time an `incremental` refresh, 17.1 s): first `search_symbols` 5 089 ms `refreshing`; wec.be 254-625 ms; after landing 143-158 ms; warm `find_field_accesses` 316-347 ms; no main-thread tick late by more than 100 ms in the 17.9 s window; `list_repositories` max 86 ms.
    - (4) `test:query-refresh` (the B.1 repros) 19/19 through the worker path.
  - **Guarded:** `refreshWorkerClient.test.ts` (6: request shape and lazy spawn, warm-up, result + `onRunLanded`, a run error rejects only that run, crash/exit reject all and respawn, dispose, spawn failure); `freshness.test.ts` (+2: two calls racing through an async tree read start one run; a failed run answers stale, releases the lock, the next query retries); `runPolicy.test.ts` (+1: when the edge indexes are dropped); `headFromFiles.test.ts` (4, against real git: loose ref and subdirectory, packed-refs, detached, linked worktree, unborn). `test:freshness-worker` (new harness, 14 checks: a 1 500-file generated repo with 300 files made dirty and a small second repo; the server runs with a test-only main-thread lag sampler preloaded (`scripts/test/_lagSampler.mjs`, `node --import`; nothing in `src/`); the first query answers within budget + 1 s as `refreshing`, every search on the other repo < 1 s, no main-thread block > 250 ms and `list_repositories` < 250 ms throughout, the edit is found after landing; then the real worker, with the latest run's `index_version` forced to `v99-from-the-future`, refuses the run — no run row, no symbol). Against the release-I build the same harness fails four checks (max block 2 074 ms, other-repo search 1 905 ms).
  - **Not done:** a tool's own synchronous work still runs on the server thread — `search_regex` reads every file synchronously (0.7 s on wec.aria idle, 3.2 s while the refresh's parse workers load the CPU), and a concurrent call waits behind it; `search_symbols` with no name hit pads with a vector KNN (~250 ms on the fixture). The refresh still runs the whole post-phase (whole-DB FTS rebuild, every unresolved call row of the repo) for a 5-file dirty run, so wec.aria shows `refreshing` for ~15 s after an edit (accepted for this release). One refresh worker per process: refreshes of two repos share one connection and interleave at their yields, as they did on the server thread. An explicit `index_repository` (server thread) of one repo while the worker refreshes another now contends for SQLite's single write lock across two connections in one process; a server-thread write waits synchronously (`busy_timeout`) for the worker's current transaction — the same contention two server processes sharing one DB always had.
