## MCP-ISSUE-088 — a refreshed answer waits ~2.3 s around a 0.35 s run

- **Status:** ✅ FIXED 2026-10-22 (release K3, 883e6b9; found by the wec.aria reviewer during the release J re-check of bf9c437).
- **Scenario:** after a 1-file add, delete or revert in wec.aria, the first query answers `refreshed` in 2.7–3.3 s while the dirty run itself records 0.34–0.97 s in `index_runs`. About 1.3 s goes before the run starts (gate: `git status`, ledger, lock, worker hand-off) and about 1 s after it (landing: worker → server message, cache invalidation, the answer's own query).
- **Tool/query attempted:** `search_symbols` timed by the reviewer's probe sequence; `index_runs.elapsed_ms` read back for the same runs.
- **Expected vs actual:** expected the wait ≈ run time plus a small constant; got a fixed ~2.3 s that is now most of the wait.
- **Impact:** every refreshed answer pays it; the 5 s budget hides it but the warm bar ("refreshed within budget") leaves little room.
- **Profiled** (temporary env-gated trace points on both sides of every hop; wec.aria clone, 1 untracked file added then deleted, 4 rounds of ~2.1-2.4 s): gate `git status` 113-123 ms; a SECOND `git status` in the worker (`collectDirtyFiles`) 110-190; profile decision + pipeline prep ~90; pipeline 100-250; then the post-phase, repo-wide on every scoped run — call re-resolution of all 5 912 still-unresolved rows ~160, CSS pass 180-190, SQL pass 318-327, cross-repo 177-183, dedup 85-119, mentions (reset + resolve all 18 324) 395-432 — then the end-of-session PASSIVE checkpoint 266-292 BEFORE the result was posted; landing + answer 60-75. The reviewer's "1.3 s before / 1 s after" was ~0.35 s before and ~0.3 s after; the rest was the run's own post-phase.
- **Fix** (each step exact by construction):
  - P1: the gate hands its tree read to the worker's dirty run (`RunExtras.knownDirtyPaths`) — the same porcelain-v2 read `collectDirtyFiles` makes, so the run indexes exactly what the gate keys freshness and the ledger on (`statusPorcelain.test.ts`: modified file, staged rename, untracked dir, deleted file — the gate's read, the run's read and the ledger are one set).
  - P2: the refresh worker posts the result, THEN runs `endIndexSession` (`deferSessionEnd`). It is synchronous, so no run the worker receives next starts before it returns; the server connection never checkpoints (release J), so it is the only checkpointer.
  - P3 (`ScopeInputs`, from the pipeline: re-extracted files incl. dependents, removed files, K names, path keys, old ids, lanes): call re-resolution only for rows of re-extracted files or whose callee names a K symbol; the CSS pass only if a written or removed file had (before the write) or has (after it) CSS rows; the SQL pass likewise, or when a written or removed file's path keys or a K name meet a `sqlconst:` anchor's token parts (an anchor binds through a module and one barrel hop that may hold no SQL row); bound mentions reset only for old ids, K name forms (exact, lower-case, dotted suffix and prefix) and path keys (`resetMentionsForScope`). Dedup stays repo-wide (~90 ms; the reviewer's condition (d) was not implemented). Cross-repo stays repo-wide (agreed: it re-links against the other repos' current state, as a full run does).
  - Found by the new conformance case `mention-prefix-delete`, both present since release J: (a) a dirty run whose ONLY change was a deleted file never queued its dependents — `queueDependentFiles` ran after the last extraction batch and there was none — so its callers kept edges into nothing, which the safety net then deleted where a full run keeps tokens; (b) a section naming a mention twice stored two rows with a NULL `symbol_id` (NULLs never conflict in the primary key), collapsed to one when bound, so a scoped run that unbound it held one row where a full run held two — `upsertDocMentions` now writes one row per (doc, type, text, symbol).
- **Measured** (wec.aria clone @ 58584fa7):
  - Conformance — 13 scenarios, dirty AND incremental each EQUAL to a full run on every table, I1 = I2 = 0: the 9 of release J plus `sql-gain` (a TS file gains its first query literal), `sql-lose` (`db-quality.ts` loses its only one, an anchor target), `css-define` (a second `--space-2`, 289 users) and `mention-prefix-delete` (`packages/core/prompt/date.ts`, mentioned in docs as `date`, deleted).
  - Gate removal (temporary `K_BREAK` hooks, reverted): SQL gate off → `sql-gain` / `sql-lose` / `sql-redefine` DIFF (2 / 111 / ~600 edges); CSS gate off → `css-define` DIFF (3 608 / 5 824 edges); the re-extracted-files clause of the call filter off → `shift` DIFF (7 686 edges); the whole mention reset off → `mention-prefix-delete` DIFF (13 rows). Two clauses do NOT fail alone on real data, because another rule already covers them: the K-name clause of the call filter (a file holding a token whose parts meet K is a release-J dependent, so it is re-extracted) and the old-id clause of the mention reset (every old id's name is in K, and the name forms cover every key the resolver uses). Both are kept; `mentionAmbiguity.test.ts` shows the old-id clause working where names are not supplied.
  - Live (spawned server, warm, 5 rounds × add / delete / edit / revert of one file): first call median 1 038 ms over 20 (min 1 013, max 1 232), every one `refreshed` with the right answer; first round after start 1 059-1 418 ms; 126 lag heartbeats, 0 samples > 100 ms. Was ~2.3 s.
- **Guarded:** `scopedRunConformance.test.ts` (`delete-only` — fails without fix (a): edges; without fix (b): doc_mentions), `statusPorcelain.test.ts` (P1), `mentionAmbiguity.test.ts` (the scoped mention reset), `test:query-refresh`, `test:freshness-worker`.
- **Follow-up after the reviewer's live check of 409f092** (median ~1.67 s on the live checkout with 5 peer-dirty files):
  - 010c16b: a dirty run skips a dirty file whose content hash equals the stored one (as incremental mode does), so files a peer session left dirty are not re-extracted by every refresh. `scopedRunConformance.test.ts` "files that stay dirty" reads "3 changed" and fails without it.
  - 8b505cc, after a per-pass profile of a 0-changed and a 1-changed refresh (0 changed: call context 94, imports/types/properties/implements ~85, cross-repo ~220-250, dedup 168, mentions 274 ms): a scoped run that wrote and removed nothing skips every post-phase pass but cross-repo (the graph is the one the last run left, and they are pure functions of it); dedup runs among the re-extracted files' edges only unless a repo-wide CSS / SQL pass ran (condition (d), done); mentions re-decide only the rows the run unbound, the fresh rows of re-extracted docs and unbound rows whose text meets a changed name, filtered in SQL. resolve_phase_ms 926 → 240 (0 changed; cross-repo is what is left), 833 → 507 (1 changed).
  - Accepted live by the reviewer on 8b505cc, the live wec.aria checkout with its 5 peer-dirty files, under load (1.2 GB free, CPU 40%): warm first calls 1 134-1 708 ms, median ~1 390 ms over 6 rounds; every run "scoped: 1 changed, 0 dependent"; cold after reconnect 3 087 ms.
  - A "0 changed" refresh still runs (the gate cannot know content is unchanged without hashing on the server thread, which K1 removed); it now costs hashing plus cross-repo. Agreed with the reviewer.
